# DirectStorage initialisation diagnostic

This diagnostic must not run until explicitly reviewed and the isolated Wine prefix is idle. It dynamically loads an absolute Windows path to the game's existing `dstorage.dll`, resolves `DStorageGetFactory`, queries `IDStorageFactory`, then requests and releases a file-source queue with a null D3D12 device. With explicit `--gpu`, it also creates a D3D12 device and a file-source DirectStorage queue bound to that device. No file is opened or submitted to either queue; no GPU destination or decompression operation is submitted. Loading a DLL or creating a device executes code and may create runtime threads; treat the process and private wineserver as owned resources and reap them.

The SDK is Microsoft's `Microsoft.Direct3D.DirectStorage` NuGet package 1.2.2: https://www.nuget.org/packages/Microsoft.Direct3D.DirectStorage/1.2.2 . Its headers are MIT-licensed; the package and extracted headers/license are temporary under `Products.noindex/dstorage-diagnostic-sdk`. Only headers were used to compile: no SDK DLL is copied to a prefix or game.

Build from the repository root after placing the official headers under `Products.noindex/dstorage-diagnostic-sdk/native/include`:

```sh
x86_64-w64-mingw32-g++ -std=c++17 -O2 -Wall -Wextra -Werror -Wno-cast-function-type -static -municode -Wl,--no-insert-timestamp -I Products.noindex/dstorage-diagnostic-sdk/native/include probes/dstorage-diagnostic.cpp -o Products.noindex/dstorage-diagnostic-gpu.exe -lole32 -luuid
```

`static_assert` checks the x64 queue-descriptor size and offsets. The factory and queue GUIDs are taken from the SDK header; literals avoid missing MinGW `__mingw_uuidof` specializations. The output is PE32+ x86-64. Neither compile nor PE inspection validates the runtime ABI.

After independent review, a future scoped controller can launch `[wine, absolute_host_probe_path, absolute_windows_dstorage_dll_path, nonce]` via `subprocess.Popen` without a shell, with a fresh nonce, the validated game D3DMetal environment, and a previously checked idle private prefix. The DLL argument can use the prefix's verified `Z:` mapping; do not assume a mapping without checking it. Preserve stdout and stderr separately, bound duration/output, and only shut down the owned private prefix after checking process and prefix identity.

Appending `--gpu` is an explicit device-creation request. The probe requires a complete DXGI adapter enumeration, rejects software adapters, and proceeds only if exactly one adapter matches the already observed game compatibility identity `1002:66af`, subsystem 0, revision 0. It reports the match count, IDs, flags and LUID so the controller can compare them to the game's observed adapter; this tuple alone does not prove the same physical device or loaded Apple backend. It creates a D3D12 device at minimum feature level 11.0 and passes that device to `IDStorageFactory::CreateQueue`. CPU queue and GPU-bound queue results remain separate; the CPU queue is released before creating the latter. A missing symbol, incomplete enumeration, ambiguous match, failed HRESULT, null object, crash or timeout is a failed or inconclusive stage. No fallback adapter or capability is fabricated.

**Executable-directory constraint.** Microsoft's [SDK path documentation](https://github.com/microsoft/DirectStorage/blob/main/Docs/DeveloperGuidance.md#sdk-path) says that `dstoragecore.dll` is normally sought beside the main executable, unless that executable exports `DStorageSDKPath`. Therefore a probe run directly from `Products.noindex` does not reproduce the game's layout even when passed the game's `dstorage.dll` by absolute path. In the recorded isolated run, factory returned `0x80004001` and no core was present at observation time; an executable-directory mismatch is a plausible explanation, not a demonstrated cause or a result for the game. Inspection of the currently installed game PE's named export table found neither `DStorageSDKPath` nor `DStorageSDKVersion`.

The reviewed next experiment is to place a temporary copy of this exact probe PE beside `Spider-Man2.exe`, under a unique `Playmelt-DStorageProbe-<nonce>.exe` name; verify its SHA-256 and the existing DLL identities before launch. Do this only after the game and selected private prefix are idle. The controller must retain the new file's identity and hash, stop/reap only its own private-prefix processes, and remove only that exact unchanged task-owned temporary probe in `finally`. Do not copy, replace, patch or remove any game DLL. The location aligns the default core lookup with the game's layout; it does not make the probe equivalent to the game's GPU or asset workload.

The single JSON output has `schema:1`, `kind:"playmelt-dstorage-probe"`, a caller-supplied ASCII `nonce`, load/symbol errors, module paths and HRESULT/object-presence pairs. Accept it only when the process exits zero without timeout and exactly one typed JSON response has the expected nonce and paths. Exit zero by itself reports completion of the diagnostic, not DirectStorage success: assess each `called`, `hresult` and `object_nonnull` field. A missing or ambiguous response, crash, timeout, other module path, or unavailable inspection is unknown/failure, never a pass.

A successful factory, D3D12 device and GPU-bound DirectStorage queue establishes only those object-creation steps in that process. It does not prove a GPU request, GPU decompression, actual disk throughput or latency, the reason for game initialisation failure, asset loading, visuals, frame pacing or compatibility of the game. Logical Wine module paths alone do not establish native module provenance. Queue creation has no reasonable ability by itself to explain a measured FPS cost or storage bottleneck; a successful queue is a prerequisite, not a performance measurement.
